# Sprint 4 Review 与学习回顾

> Product Owner 于 2026-08-22 确认结束 Sprint 4。

## Sprint Review

Sprint 4 完成了一次产品定位和架构升级。网站不再强调“学生部门官方通知平台”，而是侧重自由、极客、表达、传承与积淀。界面改为简约侧栏；主题收敛到浅色与深色；文档、文章、成员身份和个人主页形成统一入口。

系统仍是 GitHub Pages 上的静态 Astro 网站，但浏览器会连接 Supabase：

```text
Astro / GitHub Pages
├── 主页与内置 Markdown 文档
├── 页面布局、搜索与主题
└── 浏览器中的 Supabase 客户端
    ├── Auth：邮箱验证码登录
    ├── Postgres：资料、角色、文章、申请
    └── Storage：头像、背景和文章图片
```

## 本轮学习要点

### 1. 静态网站也能接入动态数据

“静态”描述的是页面如何托管，不代表页面不能在浏览器中请求数据库服务。当前没有自建服务器，但 Supabase 承担了托管后端职责。

### 2. Publishable key 可以公开，权限规则不能省

浏览器必须拿到 Supabase URL 和 publishable key 才能访问服务。真正的安全边界是登录身份、RLS、数据库约束和受控函数。Secret/service-role key 不能进入前端或仓库。

### 3. 数据库迁移类似数据库的 Git 历史

`supabase/migrations/` 记录结构和权限如何演进。新增迁移文件不等于线上数据库已经自动执行；部署前必须确认迁移已应用。

### 4. 身份、角色与内容状态是不同概念

- 身份：用户是否登录。
- 角色：用户是否为管理员。
- 内容状态：文章是草稿还是已发布。

把三者分开，权限逻辑才不会混乱。

### 5. 内容型网站需要兼顾结构与阅读细节

分类、目录、贡献者、字体、代码块和复制反馈虽然不是大型功能，却直接决定文档是否好用。Sprint 4 后期大量时间用于这些细节，符合上一轮“先搭结构、再集中整理”的改进方向。

## Retrospective

### 做得好的地方

- 能根据产品定位及时删除不再适合的复杂主题。
- 没有为了动态功能购买和维护自建服务器。
- 权限逻辑下沉到 Supabase RLS，而不是只隐藏前端按钮。
- 小步提交并持续通过构建检查。

### 可以改进

- Sprint 4 范围扩大较多，包含视觉重构、认证、个人主页和发布系统，超出理想的单一 Sprint Goal。
- Supabase 控制台配置与仓库迁移之间缺少统一验收清单。
- 动态文章未进入全站搜索，内容来源形成两套索引路径。
- 编辑器仍使用已弃用的 `document.execCommand`，虽可用但应在后续技术债 Sprint 替换。
- 之前几个 Sprint 的当前状态文档没有随分支切换及时更新。

## 后续建议

Sprint 5 开始前先确定一个主要目标，避免再次同时扩张视觉、内容和权限。优先候选包括：

- 统一动态文章与静态文档搜索；
- 手机端适配与无障碍；
- 文章编辑器重构；
- 活动/服务内容；
- 数据库迁移和发布验收自动化。

## 关闭结论

Sprint 4 的核心功能、构建检查、Product Owner 验收和回顾均已完成，Sprint 4 正式关闭。
