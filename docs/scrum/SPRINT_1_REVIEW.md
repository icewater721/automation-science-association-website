## 概念地图

```text
Astro 页面
├── Layout：所有页面共用的 HTML 骨架
├── Component：导航、搜索、部门区块等可复用界面
├── Data：部门、联系信息等可独立修改的内容
└── CSS Variables：三种主题共享的颜色规则

构建过程
源码 → Astro 检查 → 静态 HTML/CSS/JavaScript → dist/

全站搜索
结构化索引 → 浏览器按关键词匹配 → 跳转到站内页面或区块
```

## 本轮需要认识的概念

### 组件与内容分离

- 组件决定内容怎么排列、怎么交互。
- 数据文件保存部门职责、邮箱等可能更新的实际内容。
- 两者分离后，日常内容维护不容易破坏页面布局。

目标程度：认识，并能找到内容文件。

### 响应式布局

- 同一份页面会根据屏幕宽度调整列数、边距和导航排列。
- 当前已具备响应式规则，但手机真机体验留到正式域名上线后验收。

目标程度：认识。

### 静态搜索

- 搜索内容在构建网站时生成，不需要实时查询数据库。
- 浏览器下载搜索索引后，在本地完成关键词匹配。

目标程度：能够解释为什么当前搜索不需要服务器数据库。

### 主题变量

- 页面组件不为每种主题复制一份代码。
- 浅色、深色和明日方舟风格通过同名 CSS 变量替换颜色与装饰。

目标程度：认识。

## 本轮关键决策

- 首页取消独立品牌首屏，直接进入科协与部门介绍，提高信息密度。
- 部门介绍保留 A｜B｜C 切换，内容采用左侧简述、右侧职责的双栏布局。
- 明日方舟视觉只作为独立模式，普通浅色和深色模式保持克制。

## 知识检查

1. `.astro` 页面、组件和 `data/` 内容文件分别负责什么？
2. 为什么当前全站搜索不需要数据库？
3. 如果只想修改联系邮箱，应该修改哪个文件？
4. `src/` 与 `dist/` 的区别是什么？
5. `pnpm dev` 和 `pnpm build` 分别在什么时候使用？

## 知识检查结果

Product Owner 已能够用自己的话说明：

- Sprint 内的任务可以调整，但需要维持 Sprint Goal 并记录范围变化。
- 邮箱等业务内容应修改 `data/` 内容文件，而不是布局组件或 `dist/`。
- `dist/` 来自源码构建，不能作为日常修改入口。
- 当前网站内容少，静态搜索索引不需要数据库。
- `pnpm dev` 用于实时开发，`pnpm build` 用于最终导出。

## Retrospective

### 做得好的地方

- 通过多轮视觉反馈逐步找到合适的信息密度和内容布局。
- 需求发生变化时同步调整 Sprint 范围，没有把所有未来功能都挤进本轮。
- 保持静态架构，没有为尚未出现的发布需求提前建设数据库和后台。
- 每次重要修改后都运行类型、构建和格式检查。

### 出现的问题

- 开发工具最初依赖 Codex 内置环境，用户自己的 Node.js 与 pnpm 不完整。
- 本地服务器和外部网络问题多次影响页面查看与推送。
- “服务”曾错误指向主页锚点，说明页面入口与主页区块的边界需要先确认。
- 视觉需求主要通过边做边看确认，早期版本的信息密度偏低。
- 视觉效果和正式内容占用了本轮最多的讨论与调整时间，功能骨架的推进节奏受到影响。

### 后续改进建议

- 新 Sprint 开始前先确认页面、主页区块和外部入口三者的边界。
- 视觉开发先确定内容最大宽度、信息密度和栏目结构，再添加风格装饰。
- 正式域名可访问后，用真实手机完成导航与响应式验收。
- 活动迭代先设计内容模型，再实现活动列表和详情页。
- 下一阶段优先搭建网站结构并跑通功能流程，当轮只保证内容准确、界面可用。
- 每完成 2～3 个功能 Sprint，集中安排一个内容与视觉整理 Sprint。
- 基础可读性、明显布局错误和功能可用性仍在当前 Sprint 修复，不积压到整理 Sprint。
