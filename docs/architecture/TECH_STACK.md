# 技术栈建议

> 状态：已确认，2026-08-16。

## 推荐方案

| 层次       | 技术                                 | 用途                                     |
| ---------- | ------------------------------------ | ---------------------------------------- |
| 页面框架   | Astro                                | 组件化开发，并在构建时生成静态 HTML      |
| 编程语言   | TypeScript（严格模式）               | 为组件属性和内容字段提供类型检查         |
| 样式       | 原生 CSS + 语义化设计变量            | 实现黑白双主题、轻微导航分层和响应式布局 |
| 内容       | Astro Content Collections + Markdown | 管理新闻、通知、活动等结构化内容         |
| 客户端脚本 | 少量原生 TypeScript                  | 主题切换、全站搜索、移动导航等交互       |
| 搜索       | 构建时 JSON 索引 + 原生 TypeScript   | 在无后端与数据库时实现小型全站搜索       |
| 包管理     | pnpm                                 | 管理依赖和开发命令                       |
| 代码质量   | Astro Check、ESLint、Prettier        | 类型、语法和格式检查                     |
| 浏览器测试 | Playwright                           | 验证主页、响应式布局和主题切换           |
| 版本管理   | Git                                  | 保存可回滚的开发历史                     |
| 部署       | 静态托管，平台待定                   | 发布构建产物 `dist/`                     |

## 为什么选择 Astro

- 网站是内容型公开主页，不需要把整个页面做成浏览器端应用。
- 默认静态输出，不需要运行 Node.js 后端服务器。
- 支持组件化，但只向浏览器发送真正需要的 JavaScript。
- Content Collections 可以验证同类内容的字段并提供 TypeScript 类型。
- 构建结果是普通 HTML、CSS 和 JavaScript，可部署到多种静态服务器。
- 将来需要 React 组件、CMS 或按需服务器渲染时仍有扩展路径。

## 未选择方案

### Vite + React

优点是 React 生态广、学习资料多，适合交互密集的 Web 应用。当前主页以静态展示为主，整页 React 会增加不必要的客户端运行时和状态设计。

### Next.js

Next.js 支持静态导出，也能为未来全栈功能提供较多能力。但当前项目不需要服务器组件、服务端操作和复杂路由，初期概念与部署约束更多。

### 纯 HTML/CSS/JavaScript

第一版可以很快完成，但内容、组件和页面结构容易混在一起；随着栏目增加，复用、校验和维护成本会提高。

## 明确不引入

- 数据库
- 用户认证与权限库
- 管理后台
- 全局状态管理库
- UI 组件库
- CSS 工具框架
- 运行时后端服务

如果出现真实需求，再通过架构决策记录评估，而不是预先安装。

## 部署假设

第一版生成 `dist/` 静态文件，因此技术实现不绑定某家云平台。正式部署前仍需确认学校服务器、域名、备案、HTTPS 和校内网络要求。
